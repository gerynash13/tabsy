# tabsy

**フリーランス・小規模事業者向けの督促メール自動化ツール。「支払いを催促する気まずさ」を仕組みで解決します。**

日本市場を第一に設計しています。日本のB2B取引では振込が基本的な支払い手段であり、カード決済はむしろ例外です。本プロジェクトはこの前提を後付けではなく、設計の出発点として組み込んでいます。

## 課題

フリーランス・コンサルタント・小規模な代理店は、未払い請求書の督促に多くの時間と労力を奪われています。督促のタイミングを覚えておく、気まずい催促メールを書く、誰の支払いが遅れているか把握できなくなる——こうした作業は本業ではありません。既存のエンタープライズ向け債権管理ツール（Monk、Gaviti、Centimeなど）は経理部門を前提としており、一人で事業を回すフリーランスには過剰です。tabsyはこの隙間を埋めるツールです：請求書を記録し、適切なタイミングで督促メールを自動送信し、誰がいくら未払いなのかを一目で把握できるようにします。

**開発初週に下した設計判断:** tabsyは請求書の「発行ツール」ではなく「督促レイヤー」として位置づけています。ユーザーは請求書のデータを記録し（他のツールで作成したPDFを添付することも可能）、tabsy自体が請求書の原本を発行するわけではありません。この判断により、コア機能をシンプルに保ちつつ、日本のインボイス制度（適格請求書等保存方式）対応の大部分を初期スコープから切り離すことができました——ただし、後にPDF生成機能を独立した機能として明確にスコープした際は、その対応を回避するのではなく、きちんと実装しています（詳細は後述）。

## 主な機能

**コア機能**
- マジックリンク認証（パスワード不要——メールアドレスのみの単一フローにおいて「新規登録」と「ログイン」を区別する意味がないため、パスワード機構を実装するのは純粋なオーバーヘッドと判断しました）
- 顧客・請求書管理、CSVインポート対応（Shift-JIS/CP932に対応——日本語ロケールのWindows版Excelから出力されるCSVを想定）
- ダッシュボード：未回収金額（通貨ごとにグループ化して表示。異なる通貨を合算することはしません）、支払期日が近い請求書・延滞中の請求書の一覧
- 請求書のステータス（未払い／延滞／支払済み）は、督促メールを送信する同じバッチ処理によって自動的に更新されます

**督促エンジン**
- 督促タイミングを設定可能（デフォルト：支払期日の3日前、当日、3日後、7日後、14日後）。段階が進むにつれて文面のトーンも丁寧から徐々に強めに変化します
- 1日1回実行。サーバー自体のタイムゾーンに関わらず、「本日が支払期日か」の判定は常に日本時間（JST）で行います
- 設計上、二重送信が発生しません——同じ請求書・同じタイミングの組み合わせに対して、たとえバッチ処理が誤って2回実行されても、督促メールが2通届くことはありません
- 日本語・英語のデフォルトテンプレートに加え、Groq（無料枠）によるAI下書き機能を搭載。ユーザーごと・言語ごとに編集可能で、5段階のうち1つだけを個別に再生成することも可能です

**コンプライアンス対応**
- 日本のインボイス制度（適格請求書等保存方式）に準拠したPDFをオンデマンドで生成：登録番号、明細ごとの税率、国税庁の実際のルールに基づく消費税額の計算・端数処理（詳細は後述）、法定記載事項6項目すべてに対応
- Stripeの決済リンクを督促メールに任意で挿入可能。ゼロ小数通貨（日本円など）の正しい取り扱いと、署名検証済みのWebhookによる支払い確認に対応

**その他**
- UIは日本語・英語完全対応（Cookieベースの言語設定であり、各顧客ごとの「督促メールの言語」設定とは明確に別物として扱っています）
- 複数通貨対応。ダッシュボードでは通貨ごとに集計（為替レートによる自動換算は行いません）

## 技術スタック

| レイヤー | 選定技術 | 選定理由 |
|---|---|---|
| フレームワーク | Next.js 15（App Router）、TypeScript | フロントエンド・バックエンドを1つのフレームワークに統一し、個人開発として適切な規模に抑えるため |
| DB／認証／ストレージ | Supabase（Postgres） | 認証・DB・RLSによるユーザーごとのデータ分離を一元管理でき、無料枠も十分 |
| スケジューリング | Vercel Cron（1日1回） | 1日1回のバッチで要件を満たせる。UTCで動くプラットフォームに対し、JSTを明示的に扱う設計判断を強制させる効果もあった |
| メール送信 | Resend | APIがシンプルで、この規模の実運用であれば無料枠で十分 |
| AI（テンプレート下書き） | Groq（Llama 3.3 70B、OpenAI互換API） | クレジットカード不要の無料枠。ユーザーごとに数回程度しか呼び出さず、送信時には一切使用しない |
| 決済 | Stripe Payment Links | Checkout Sessionではなく意図的にこちらを選択。Sessionの有効期限は最大24時間しかなく、17日間続く督促シーケンスには短すぎるため |
| PDF生成 | @react-pdf/renderer | ヘッドレスブラウザ不要で、サーバーレス関数上でも問題なく動作する |
| CSV解析 | papaparse + iconv-lite | 後者はShift-JISの検出・デコード専用 |
| UI | Tailwind + 独自の簡易ブランドシステム | Ledger Green／Paper／Ink／Overdue Redの配色、IBM Plex Sans + IBM Plex Sans JP |

## 特に共有したい設計判断

機能一覧だけでは、このプロジェクトで実際に難しかった部分が伝わりません。いくつか具体的に挙げます。

**「先にログを書く」ことで二重送信を防ぐ設計。** `reminder_log`テーブルには`(invoice_id, offset_days)`の組み合わせに一意制約を設けています。督促バッチはメールを送信する**前に**このテーブルへの書き込みを行います。つまり、この書き込み自体が「一度しか成功し得ない処理」になっています。仮にバッチが誤って2回実行されたり、将来的にリトライ処理を追加したりしても、どちらか一方しか成功しません。もし順序を逆にする（送信してからログを書く）と、両者の間で処理が中断した場合に実際に顧客へ督促メールが二重に届いてしまいます。

**サーバー時刻に依存しないJST計算。** Vercel Cronは常にUTCで実行されます。「この請求書は本日が支払期日か」という判定はすべて、明示的な`Asia/Tokyo`変換を行う`todayInJST()`関数を経由します。Node.jsプロセスが内部的にどのタイムゾーンを認識しているかに依存させない設計です。

**インボイス制度の消費税端数処理は、必ず一次情報を確認して実装。** インボイス制度では、消費税額の端数処理を「一つの請求書につき、税率ごとに1回」行うことが求められています——明細行ごとに端数処理をしてから合計するのは不可です。これは国税庁が公表しているルールを直接確認した上で実装しており、憶測で組んだものではありません。明細ごとに端数処理をする素朴な実装では、正しい（法令に準拠した）合計額とは異なる金額になってしまいます。

**Checkout SessionではなくPayment Linksを採用。** Checkout Sessionの有効期限は最大24時間——これはコードを書く前にStripeの公式ドキュメントで確認済みです。17日間続く督促シーケンスの途中でリンクが失効してしまっては意味がありません。Payment Linksは明示的に無効化するまで有効であり続けるため、この用途に適しています。決済完了したセッションと請求書の紐付けには、Stripeが公式にドキュメント化している`client_reference_id`を使用しています（Payment Link作成時に設定したmetadataがセッションに引き継がれる挙動は、ドキュメント上の裏付けが弱いため採用しませんでした）。

**ゼロ小数通貨を明示的に処理。** 日本円・韓国ウォンは、Stripe APIに送る際に他の通貨のように100倍する必要がありません。この一点を見落とすと、実際の100倍の金額を請求してしまうという、実害のあるバグになります。

**AIと決定論的処理の境界線。** 督促メールに含まれる金額・日付・請求書番号・振込先情報・決済リンクは、AIが下書きしたテンプレートをユーザーが編集したものであっても、常に単純な文字列置換によって挿入されます。これらの値をAIが生成することは一切ありません。テンプレート機能がどれだけ柔軟になっても、この境界線だけは動かしていません。

**為替換算をしない前提での複数通貨対応。** ダッシュボードは、異なる通貨の金額を無理に合算して誤解を招く数字を出すのではなく、通貨ごとに分けて集計します。実際の為替換算（そして「どの時点のレートを使うか」という本質的な問い）は、安易に組み込むのではなく、意図的に対応範囲から外しています。

## 開発中に見つけて修正したバグ

最初からすべて正しく実装できたわけではないという事実を、正直に記録しておきます。

- **`dotenv/config`は`.env`を読み込む仕様で、`.env.local`は読み込まない。** シードスクリプトが環境変数を一切読み込めていない状態に気づかず、`supabaseUrl is required`というエラーから原因を特定しました。
- **「送信成功」を実際には確認していなかった。** Resend SDKはエラー時に例外をスローせず、`{ data, error }`という形で返します。督促バッチの初期実装では`error`フィールドを一切確認しておらず、実際には送信が拒否されていても`"sent": true`と記録されていました。レスポンスを正しく確認するよう修正しました。
- **Stripe CLIのアカウント／サンドボックスの不一致。** `stripe listen`のログインセッションが、アプリのAPIキーとは別のアカウントに紐づいていました。Stripe側ではイベントが正しく発火していたものの、ローカルのリスナーには一切届いていませんでした。`--api-key`オプションでCLIを明示的に同じキーに固定することで解決しました。
- **認証ミドルウェアがサーバー間通信を無条件でブロックしていた。** ログイン画面へのリダイレクトを行うミドルウェアが、`/api/*`配下のルート（StripeのWebhookや、より深刻には本番環境でVercelのスケジューラが呼び出すエンドポイント）まで巻き込んでいました。手動テストでは、すでにログイン済みのブラウザタブから実行していたため問題が表面化せず、`curl`やシークレットウィンドウ（セッションなし）でテストして初めて発覚しました。ミドルウェアの対象パスから`/api/*`を除外することで解決しました。各APIルートは、Stripeの署名検証・共有シークレット・Supabaseセッションの直接確認など、それぞれ自前で認可処理を行っています。

## ディレクトリ構成

```
src/
  app/
    (app)/                    # 認証必須のルート（ダッシュボード、請求書、顧客、設定）
    api/
      cron/reminders/         # Vercel Cronが呼び出す督促バッチ本体
      webhooks/stripe/        # 署名検証済みの決済確認処理
      invoices/[id]/pdf/      # インボイス制度対応PDFのオンデマンド生成
      locale/                 # UI言語のCookieを設定
    auth/callback/            # マジックリンクによるセッション確立
    login/
  lib/
    reminders/                # JST日付計算、テンプレート、AI下書き、督促バッチ本体
    stripe/                   # 決済リンクの作成・無効化、ゼロ小数通貨対応
    invoices/                 # 税額計算（インボイス制度準拠の端数処理）、通貨一覧
    invoice-pdf/               # React-PDFによる帳票テンプレート
    csv/                      # Shift-JIS対応デコード、日付パース
    i18n/                     # 言語Cookie + 日英辞書一式
    supabase/                 # server / browser / service-role の各クライアント
supabase/
  schema.sql                  # 新規構築用のフルスキーマ
  migrations/                 # 既存DB向けの差分マイグレーション
```

## セットアップ

1. Supabaseプロジェクトを作成し、SQLエディタで`supabase/schema.sql`を実行
2. `.env.local.example`を`.env.local`としてコピーし、Supabase・Resend・（任意で）Groq／Stripeの認証情報を入力
3. `npm install && npm run dev`
4. `npm run seed`で、各督促タイミングに対応するテスト用請求書を作成し、動作確認が可能

各機能ごとの詳細なセットアップ手順や週単位の開発経緯については、[`DEVELOPMENT.md`](./DEVELOPMENT.md)（本ドキュメントの元になった開発ログ）を参照してください。

## 既知の制約

- チーム・複数ユーザー対応は未実装です。現状、すべてのテーブルのRow Level Securityは「1ユーザー＝1事業者」を前提としています。
- インボイス制度対応のPDF生成機能は、国税庁が公表しているルールを確認した上で慎重に実装していますが、**実際の申告・記帳にそのまま使う前には、必ず税理士等の専門家によるレビューを受けてください**。経過措置や代理受領など、対応スコープ外のケースも存在します。
- ダッシュボードでの自動為替換算は、意図的に非対応としています（理由は上記参照）。
