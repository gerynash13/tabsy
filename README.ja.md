# tabsy

**フリーランス・小規模事業者向けの督促メール自動化ツール。「支払いを催促する気まずさ」を仕組みで解決します。**

日本市場を第一に設計しています。日本のB2B取引では振込が基本的な支払い手段であり、カード決済はむしろ例外です。本プロジェクトはこの前提を後付けではなく、設計の出発点として組み込んでいます。

## 課題

フリーランス・コンサルタント・小規模な代理店は、未払い請求書の督促に多くの時間と労力を奪われています。督促のタイミングを覚えておく、気まずい催促メールを書く、誰の支払いが遅れているか把握できなくなる——こうした作業は本業ではありません。既存のエンタープライズ向け債権管理ツール（Monk、Gaviti、Centimeなど）は経理部門を前提としており、一人で事業を回すフリーランスには過剰です。tabsyはこの隙間を埋めるツールです：請求書を記録し、適切なタイミングで督促メールを自動送信し、誰がいくら未払いなのかを一目で把握できるようにします。

## 主な機能

**コア機能**
- マジックリンク認証（パスワード不要——メールアドレスのみの単一フローに「新規登録」と「ログイン」の区別を設ける意味がないため）
- 顧客・請求書管理、CSVインポート対応（Shift-JIS/CP932対応——日本語ロケールのWindows版Excelから出力されるCSVを想定）
- ダッシュボード：未回収金額を通貨ごとにグループ化して表示（異なる通貨は合算しません）、支払期日が近い請求書・延滞中の請求書の一覧
- 請求書のステータス（未払い／延滞／支払済み）は、督促メールを送信する同じバッチ処理によって自動更新

**督促エンジン**
- 督促タイミングを設定可能（デフォルト：支払期日の3日前、当日、3日後、7日後、14日後）。段階が進むにつれて文面のトーンも徐々に強めに変化
- 1日1回実行。サーバーのタイムゾーンに関わらず、「本日が支払期日か」の判定は常に日本時間（JST）で実施
- 設計上、二重送信が発生しない——同じ請求書・同じタイミングの組み合わせに対して督促メールが2通届くことはない
- 日本語・英語のデフォルトテンプレートに加え、Groq（無料枠）によるAI下書き機能。ユーザーごと・言語ごとに編集可能で、5段階のうち1つだけを個別に再生成することも可能

**コンプライアンス対応**
- 日本のインボイス制度（適格請求書等保存方式）に準拠したPDFをオンデマンドで生成：登録番号、明細ごとの税率、国税庁の実際のルールに基づく端数処理（詳細は[開発メモ](#開発メモ)参照）
- Stripeの決済リンクを督促メールに任意で挿入可能。ゼロ小数通貨の正しい取り扱いと、署名検証済みWebhookによる支払い確認に対応

**その他**
- UIは日本語・英語完全対応（Cookieベースの言語設定であり、各顧客の「督促メールの言語」設定とは別物）
- 複数通貨対応。ダッシュボードでは通貨ごとに集計（為替換算は行わない）

## 技術スタック

| レイヤー | 選定技術 | 選定理由 |
|---|---|---|
| フレームワーク | Next.js 15（App Router）、TypeScript | フロントエンド・バックエンドを1つのフレームワークに統一 |
| DB／認証／ストレージ | Supabase（Postgres） | 認証・DB・RLSによるユーザー分離を一元管理 |
| スケジューリング | Vercel Cron（1日1回） | 1日1回のバッチで要件を満たせる |
| メール送信 | Resend | APIがシンプル、無料枠も十分 |
| AI（テンプレート下書き） | Groq（Llama 3.3 70B、OpenAI互換API） | クレジットカード不要の無料枠 |
| 決済 | Stripe Payment Links | Checkout Sessionではない理由は[開発メモ](#開発メモ)参照 |
| PDF生成 | @react-pdf/renderer | ヘッドレスブラウザ不要、サーバーレス向き |
| CSV解析 | papaparse + iconv-lite | 後者はShift-JIS検出・デコード用 |
| UI | Tailwind + 独自の簡易ブランドシステム | Ledger Green／Paper／Ink／Overdue Redの配色、IBM Plex Sans + IBM Plex Sans JP |

## クイックスタート

```bash
git clone <このリポジトリ>
cd tabsy
npm install
cp .env.local.example .env.local   # 値を入力——下の一覧を参照
npm run dev
```

初回のみ：
1. Supabaseプロジェクトを作成し、SQLエディタで`supabase/schema.sql`を実行
2. `localhost:3000`でメールアドレスを入力してログイン（マジックリンクが届きます。パスワード設定は不要）
3. `npm run seed`で各督促タイミングに対応するテスト用請求書を作成——実際の支払期日を何日も待たずに動作確認が可能

## 環境変数

| 変数名 | 必須 | 用途 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 必須 | SupabaseプロジェクトのURL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 必須 | Supabaseのanonキー（クライアント公開可） |
| `NEXT_PUBLIC_SITE_URL` | 必須 | マジックリンクのリダイレクト先に使用 |
| `SUPABASE_SERVICE_ROLE_KEY` | 必須 | サーバー専用——督促バッチとシードスクリプトがRLSを回避するために使用。ブラウザには絶対に公開しないこと |
| `RESEND_API_KEY` | 必須 | 督促メールの送信 |
| `REMINDER_FROM_EMAIL` | 必須 | 督促メールの送信元アドレス |
| `CRON_SECRET` | 必須（本番環境） | Vercel自身によるcronルート呼び出しの認証 |
| `GROQ_API_KEY` | 任意 | AIによるテンプレート下書き機能を有効化。未設定でも他機能に影響なし |
| `STRIPE_SECRET_KEY` | 任意 | 決済リンク機能を有効化。未設定でも他機能に影響なし |
| `STRIPE_WEBHOOK_SECRET` | 任意 | `STRIPE_SECRET_KEY`設定時のみ必須——Webhook署名の検証に使用 |

## 使い方

1. **設定** — 屋号・振込先情報、（任意で）インボイス制度の登録番号を入力
2. **顧客** — 連絡先情報と、督促メールの希望言語を登録
3. **請求書** — 手動で作成するか、CSVで一括インポート。コンプライアンス対応PDFやStripe決済リンクを使う場合は明細を追加
4. **督促** — デプロイ後は1日1回、各請求書の支払期日に基づいて自動送信されます。ローカル環境やデプロイ直後は、設定画面の「今すぐ送信を確認」ボタンで即座に動作確認が可能
5. **ダッシュボード** — 未回収・支払期日間近・延滞中の状況を一目で確認

## テスト・動作確認について

自動テストスイート（Jest/Playwrightなど）は構築していません——CIパイプラインではなく、開発中の実機テストによって動作確認を行いました。この点は誤解のないよう明記しておきます。実際に行った確認方法は以下の通りです。
- `npm run seed`で督促タイミングごとに1件ずつテスト用請求書を作成。cronルートを連続で2回実行し、2回目の実行で全件`"sent": false`となることを確認——これが二重送信防止の実質的なテストです
- Stripeのテストモード（カード番号`4242 4242 4242 4242`）とStripe CLIの`stripe listen`を使い、決済リンク→Webhook→請求書の自動支払済み化までの一連の流れを確認
- PDFの税額計算については、国税庁が公表している計算例との手動照合のみで、正式な自動テストは未整備です。`src/lib/invoices/calculate.ts`は将来的な変更で気づかれずに壊れた場合、見た目上の不具合ではなくコンプライアンス上の実害に直結する箇所のため、ここは本来ユニットテストを追加すべき優先箇所だと考えています。

## トラブルシューティング

開発中に実際に遭遇した問題です。同じ問題に次に遭遇するのは（おそらく）未来の自分なので、ここに残しておきます。

- **`tsx: not found`** — 依存関係追加後に`npm install`を実行せずに`npm run seed`を実行してしまったケース。`npm install`を実行してから再度お試しください。
- **シードスクリプトで`supabaseUrl is required`エラー** — `dotenv/config`は`.env`という名前のファイルを読み込む仕様で、`.env.local`は読み込みません。シードスクリプトはこの理由から`.env.local`を明示的に読み込むようにしています。同様のパターンを他で流用する際は、`dotenv/config`のデフォルト挙動を過信しないよう注意してください。
- **生成したPDFの日本語が文字化けする** — `@react-pdf/renderer`の既定フォントには日本語グリフが一切含まれていません。`Font.register()`でNoto Sans JPを登録することで解決しました。
- **`stripe listen`が「must specify events to forward」エラーを出す** — Stripe CLIの仕様変更により、イベント形式の明示指定が必須になりました。本コードが前提とする従来形式（フルペイロード）を使うには`--all-thin`ではなく`--all-snapshot`を指定してください。
- **StripeのダッシュボードにはイベントがあるのにCLIに届かない** — CLIのログインセッションが、`.env.local`のキーとは別のアカウント／サンドボックスに紐づいています。`stripe listen --api-key sk_test_... --all-snapshot --forward-to localhost:3000/api/webhooks/stripe`のように明示的に指定してください。
- **WebhookやcronルートがHTTP 307で`/login`にリダイレクトされ、処理が実行されない** — 認証ミドルウェアが`/api/*`配下も対象にしてしまい、ブラウザセッションのないリクエスト（＝StripeのWebhookやVercelのcronスケジューラからの呼び出しはすべてこれに該当）を`/login`へリダイレクトしていました。`src/middleware.ts`の対象パスから`/api/*`を除外して解決しています。
- **CSVインポート後に顧客名が文字化けする** — 日本語ロケールのWindows版Excelは、しばしばUTF-8ではなくShift-JISでCSVを出力します。`src/lib/csv/decode.ts`がこれを検出し、Shift-JISへのフォールバックデコードを行います。

## 開発メモ

コードを実際に読む方向けに、いくつか判断の背景を残しておきます。

- **督促の二重送信防止**：`reminder_log`テーブルには`(invoice_id, offset_days)`の一意制約があり、督促バッチはメール送信**前**にこのテーブルへ書き込みます。「後から記録するログ」ではなく「一度しか成功し得ない書き込み」そのものが二重送信を防いでいます。
- **サーバー時刻に依存しないJST計算**：Vercel CronはUTCで実行されるため、「本日が支払期日か」の判定はすべて明示的な`Asia/Tokyo`変換を経由します。
- **インボイス制度の消費税端数処理**：国税庁のガイドラインを直接確認して実装——消費税額は「一つの請求書につき、税率ごとに1回」端数処理を行い、明細ごとに端数処理してから合計する方法は法令に準拠しません。
- **Checkout SessionではなくPayment Links**：Sessionの有効期限は最大24時間であることをコードを書く前にドキュメントで確認済み——17日間続く督促シーケンスには短すぎます。決済完了と請求書の紐付けには、Stripeが公式にドキュメント化している`client_reference_id`を使用しています。
- **ゼロ小数通貨への対応**：日本円・韓国ウォンは、他の通貨と異なりStripe APIに送る前に100倍しません。これを見落とすと実際の100倍の金額を請求してしまいます。
- **AIと決定論的処理の境界線**：金額・日付・請求書番号・振込先情報・決済リンクは、AIが下書きしテンプレートをユーザーが編集したものであっても、常に単純な文字列置換で挿入されます。AIがこれらの値そのものを生成することはありません。

## 既知の制約

- チーム・複数ユーザー対応は未実装——現状すべてのテーブルのRow Level Securityは「1ユーザー＝1事業者」を前提としています。
- インボイス制度対応のPDF生成機能は、**実際の申告・記帳にそのまま使う前に、必ず税理士等の専門家によるレビューを受けてください**。経過措置や代理受領などのケースは対応スコープ外です。
- ダッシュボードでの自動為替換算は意図的に非対応です。
